# Руководство контрибьютора VRXX

Спасибо за интерес к проекту VRXX! Этот документ описывает основные правила, процессы и рекомендации для участия в разработке. 

Проект представляет собой нативное Linux-приложение на `Rust` и `GTK4`, взаимодействующее с привилегированным демоном для управления VPN-тунелями (ядро Sing-box).

---

## 1. Как начать

### 1.1. Подготовка окружения
Убедитесь, что у вас установлены:
- **Rust** (через rustup, версия 1.80+)
- **GTK4** и **Libadwaita** библиотеки разработки
- **OpenSSL**, **pkg-config**, **gettext**

Пример для Ubuntu/Debian:
```bash
sudo apt update
sudo apt install libgtk-4-dev libadwaita-1-dev libssl-dev pkg-config gettext
```

### 1.2. Сборка и запуск
Склонируйте репозиторий и соберите проект:
```bash
git clone https://github.com/Mark-TinZ/vrxx
cd vrxx
cargo build
```

Помните, что для работы VPN-функционала требуется запустить демона от имени root (или через системный сервис `vrxx-daemon.service`):
```bash
# Запуск демона в фоне (ручной запуск или systemctl enable --now vrxx-daemon)
sudo ./target/debug/vrxx --daemon &

# Запуск UI (от обычного пользователя)
./target/debug/vrxx

# Запуск консольного TUI (от обычного пользователя)
./target/debug/vrxx tui
# или через отдельный бинарник
./target/debug/vrxx-tui
```

## 2. Архитектурные принципы

Проект разделён на три основных слоя:

1. **Слой UI (GTK4 & Ratatui TUI)**: Находится в `src/ui/` (GTK4 GUI) и `src/tui/` (Ratatui TUI). Отвечает *только* за отображение и взаимодействие с пользователем.
2. **Слой Backend (Daemon/IPC)**: Находится в `src/daemon/` и `src/ipc.rs`. Выполняется от `root` (системная служба `/usr/lib/systemd/system/vrxx-daemon.service`), опрашивает сокет `/run/vrxx/daemon.sock` и управляет ядром `sing-box`.
3. **Слой Domain (Логика)**: Находится в `src/domain/` и `src/settings.rs`. Отвечает за парсинг ключей и генерацию конфигов.

**Ключевые правила:** 
- **Главный поток UI:** Ни при каких обстоятельствах **не должен блокироваться**. Опрос сокета `/run/vrxx/daemon.sock` и длительные операции должны выполняться полностью асинхронно через `tokio::task` (`glib::spawn_future_local` или `async_channel`).
- **Требования к TUI (`src/tui/`):** TUI не содержит логики генерации конфигов или прямых вызовов `ip route`. Вся информация запрашивается по IPC у демона. Терминальный цикл обработки событий (`crossterm::event::read()`) работает в отдельном `tokio::task` с неблокирующим рендерингом `terminal.draw()`. Все ошибки TUI и IPC оборачиваются в `anyhow::Result` без использования `.unwrap()`.
- **Непрерывность работы:** Закрытие GUI или TUI (`q`) **не должно** останавливать фоновый процесс `sing-box`. При повторном старте интерфейс запрашивает статус по IPC и восстанавливает активное состояние.
- **Обработка URL-ссылок (Deep Linking / Scheme Handlers):** Перехват ссылок `vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://` (`hy2://`), `tuic://` регистрируется в `.desktop` файле (`MimeType=x-scheme-handler/...`). Обработка перехваченных ссылок во всех инстансах приложения должна маршрутизироваться через DBus в основной процесс (`gio::ApplicationFlags::HANDLES_OPEN` / `ApplicationImpl::open`) и отображать модальный интерактивный диалог `AdwDialog` (`import_dialog.rs`) с неблокирующим замеряющим пинг потоком `glib::spawn_future_local`.
- **Чистота и безопасность слоя Domain (`src/domain/`):** Никаких зависимостей от GTK4 / `gio` / `gdk`. Формирование конфигураций sing-box адаптивно поддерживает версии ядер 1.8 - 1.13+ с безопасной сборкой JSON и отсутствием `.unwrap()` в рабочем коде. Покрытие автотестами (`test_singbox_config_validity`) обязательно для всех поддерживаемых протоколов (VLESS, VMess, Trojan, Shadowsocks 2022/AEAD, Hysteria2, TUIC v5, WireGuard).
- **Генерация QR-кодов и шеринг профилей (`src/domain/exporter.rs` & `src/ui/qr_dialog.rs`):** Рендеринг QR-кодов производится исключительно в оперативной памяти в `gdk::Texture` без создания временных дисковых файлов. Экспорт в PNG/SVG осуществляется асинхронно через `gtk::FileDialog`. Все текстовые элементы локализуются через `gettext("...")`, а сбои отображаются через информативные уведомления `AdwToast`.
- **Модуль тестирования задержки (`src/services/ping.rs`):** Поддерживает 4 алгоритма (`ViaProxyGet`, `ViaProxyHead`, `TcpHandshake`, `IcmpPing`), настраиваемый URL (по умолчанию `https://www.gstatic.com/generate_204`) и таймаут 3 секунды. Ошибки пинга заворачиваются в безопасный enum `PingResult` без `.unwrap()` и без паник. Массовый пинг списка профилей выполняется параллельно через `tokio::spawn` с лимитом `buffer_unordered`, а результаты доставляются в поток UI через `async_channel` / `glib::spawn_future_local` без блокировки интерфейса.
- **Самовосстановление сети (Self-Healing Network):** При старте `vrxx-daemon` в обязательном порядке выполняется `network::self_heal()` (`src/daemon/network.rs`) для удаления сиротских `vrxx-tun` интерфейсов, очистки зависших правил таблицы маршрутизации (`table 100`) и сброса режима `org.gnome.system.proxy mode` в `"none"`.
- **Диалоги критических ошибок (`src/ui/error_dialog.rs`):** Ошибки подключения VPN выводится пользователю через модальный `AdwAlertDialog` с кнопкой «Скопировать технический лог» ("Copy technical log"), которая пишет стек ошибки и диагностики в системный буфер обмена (`GdkClipboard`). Ни одна сетевая или системная ошибка не должна вызывать панику (`panic!`) или аварийное завершение GUI-приложения.

## 3. Стандарты кода (Rust)

Мы стремимся поддерживать чистоту и надежность кодовой базы. 

### 3.1. Обязательные проверки
Перед созданием коммита или Pull Request всегда выполняйте:
```bash
# Форматирование кода
cargo fmt

# Линтинг (предупреждения должны быть исправлены)
cargo clippy -- -D warnings

# Запуск тестов (требует xvfb-run для GTK)
xvfb-run cargo test
```

### 3.2. Обработка ошибок (Никаких `.unwrap()` и `.expect()`)
- Использование `.unwrap()` или `.expect()` **строго запрещено** в основном коде приложения и модулях IPC (допускается только в автотестах).
- Ошибки сокета, IPC-запросов и выполнения команд ядра обязаны заворачиваться через `anyhow::Result` или пользовательские типы ошибок `thiserror`.
- При необходимости вернуть значение по умолчанию, используйте `unwrap_or()` или `unwrap_or_default()`.

### 3.3. Логирование и событийно-ориентированная трансляция
- Вывод системных и сетевых событий выполняется **исключительно** через макросы из крейта `tracing`: `tracing::info!`, `tracing::warn!`, `tracing::error!`, `tracing::debug!`.
- Запрещено использовать `println!` в коде приложения.
- Все логи процесса `sing-box` и самого демона автоматических подхватываются `TracingLayer` и транслируются графическому клиенту по IPC/SSE каналам.

## 4. Процесс разработки (Git Flow)

### 4.1. Ветвление
- Основная ветка разработки — `main`.
- Для новой фичи или бага создавайте отдельную ветку от `main`:
  `git checkout -b feature/name-of-feature` или `git checkout -b fix/issue-description`

### 4.2. Коммиты
- Делайте атомарные коммиты (один коммит = одно логическое изменение).
- Сообщения коммитов должны быть осмысленными и описывать *что* и *зачем* было сделано.

---

## 5. Создание Pull Request (PR)

### Чеклист перед отправкой PR:
- [ ] Ветка синхронизирована с последним состоянием `main` (`git rebase main`).
- [ ] Код отформатирован (`cargo fmt`).
- [ ] Clippy не выдает предупреждений (`cargo clippy -- -D warnings`).
- [ ] В коде нет вызовов `.unwrap()` или `.expect()`.
- [ ] Тесты проходят (`xvfb-run cargo test`).
- [ ] Логирование использует `tracing::info!` / `tracing::error!`.
- [ ] Опрос IPC-сокета реализован асинхронно в `tokio::task` без блокировки GTK main loop.
- [ ] Если добавлены новые текстовые строки в UI, они обернуты в `gettext("...")` или `translatable="yes"`.
- [ ] Если архитектура была изменена, соответствующий файл в `docs/` обновлён.

Опишите в PR, какую проблему он решает и как вы это протестировали.

---

## 6. Локализация (i18n)

Если вы добавляете новый текст в интерфейс:
1. В Rust-коде: `gettextrs::gettext("My text")`
2. В `.ui` XML-файлах: `<property name="label" translatable="yes">My text</property>`
3. После добавления строк, перегенерируйте `.pot` шаблон и обновите файлы в папке `po/`. Подробнее см. `docs/08-localization.md`.
