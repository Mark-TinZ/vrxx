# Руководство контрибьютора VRXX

Спасибо за интерес к проекту VRXX! Этот документ описывает основные правила, процессы, стандарты комментирования и рекомендации для участия в разработке. 

Проект представляет собой нативное Linux-приложение на `Rust` и `GTK4 / Libadwaita`, взаимодействующее с привилегированным демоном (`vrxx-daemon`) для управления VPN-туннелями (сетевое ядро Sing-box) и предоставляющее как графический (GUI), так и консольный (TUI) интерфейсы.

---

## 1. Как начать

### 1.1. Подготовка окружения
Убедитесь, что в вашей системе установлены:
- **Rust** (через rustup, стабильная версия 1.80+)
- **GTK4** (>= 4.14) и **Libadwaita** (>= 1.5) библиотеки разработки
- **OpenSSL**, **pkg-config**, **gettext**

Пример установки зависимостей для Ubuntu/Debian:
```bash
sudo apt update
sudo apt install libgtk-4-dev libadwaita-1-dev libssl-dev pkg-config gettext
```

Пример для Arch Linux / Fedora:
```bash
# Arch Linux
sudo pacman -S gtk4 libadwaita openssl pkgconf gettext

# Fedora
sudo dnf install gtk4-devel libadwaita-devel openssl-devel pkgconf gettext
```

### 1.2. Сборка и запуск
Склонируйте репозиторий и соберите проект:
```bash
git clone https://github.com/Mark-TinZ/vrxx
cd vrxx
cargo build
```

Для полноценной работы VPN-функционала требуется запустить демона от имени `root` (или активировать системный сервис `vrxx-daemon.service`):
```bash
# 1. Запуск демона в фоне (ручной запуск от root)
sudo ./target/debug/vrxx --daemon &

# 2. Запуск графического интерфейса GUI (от обычного пользователя)
./target/debug/vrxx

# 3. Запуск консольного терминального интерфейса TUI (от обычного пользователя)
./target/debug/vrxx tui
# или через отдельный бинарник:
./target/debug/vrxx-tui
```

## 3. Архитектурные принципы

Проект разделён на четкие слои ответственности:

1. **Слой UI (GTK4 & Ratatui TUI)**:
   - `src/ui/` (GTK4 GUI на базе Libadwaita 1.5+)
   - `src/tui/` (Ratatui TUI для работы в терминале)
   - Отвечает *только* за отображение данных и взаимодействие с пользователем.
2. **Слой Backend (Daemon & REST API / SSE IPC)**:
   - `src/daemon/` и `src/ipc.rs`.
   - Запускается от `root` (системная служба `vrxx-daemon.service`), слушает локальный порт `http://127.0.0.1:13337` и управляет процессом ядра `sing-box`.
   - Передает события, изменение статуса и логи клиентам через Server-Sent Events (`/api/events`).
3. **Слой Domain (Бизнес-логика)**:
   - `src/domain/key_parser.rs`: парсинг ссылок протоколов (VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, WireGuard) и валидация.
   - `src/domain/singbox_config.rs`: генерация валидной конфигурации sing-box (спецификация 1.13.18+).
   - `src/domain/exporter.rs`: генерация QR-кодов в векторном SVG и растровом PNG форматах в оперативной памяти.
4. **Слой фоновых сервисов**:
   - `src/services/ping.rs`: замер сетевой задержки (4 алгоритма) и E2E Warm-Up проверка доступности туннеля.
   - `src/services/geo_updater.rs`: загрузка и обновление бинарных баз GeoIP/GeoSite (`.srs`) с поддержкой CDN fallback.

### Ключевые правила разработки:
- **Главный поток UI:** Ни при каких обстоятельствах **не должен блокироваться**. Сетевые запросы к REST API демона, DNS-резолвинг, парсинг и замеры задержки выполняются асинхронно через `glib::spawn_future_local` или `tokio::spawn` с передачей результатов через `async_channel`.
- **Автономность TUI (`src/tui/`):** TUI не содержит прямой логики настройки маршрутов ядра и работает исключительно через IPC-клиент `DaemonClient`.
- **Непрерывность работы ядра:** Закрытие GUI или TUI **не останавливает** фоновый процесс ядра VPN. При повторном открытии интерфейс запрашивает текущий статус по REST API и восстанавливает активное состояние.
- **Безопасность памяти в GTK (Weak References):** В таймерах (`glib::timeout_add_local`), асинхронных задачах и замыканиях сигналов всегда используйте слабые ссылки (`let page_weak = self.downgrade();`) с проверкой `page_weak.upgrade()` для исключения циклических ссылок и утечек памяти.
- **Стилизация (Libadwaita HIG):** Используйте только стандартные именованные классы и системные палитры (`@accent_bg_color`, `@window_bg_color` и т.д.). Запрещен хардкод цветов и инлайн-CSS строками в коде компонентов.
- **Самовосстановление сети (Self-Healing):** При старте демона `network::self_heal()` удаляет зависшие интерфейсы `vrxx-tun`, устаревшие правила маршрутизации (`table 100`) и сбрасывает режим системного прокси GNOME в `"none"`.

## 4. Стандарты кода (Rust)

### 4.1. Обязательные проверки перед коммитом:
```bash
# 1. Форматирование кода
cargo fmt

# 2. Линтинг (предупреждения должны отсутствовать)
cargo clippy --all-targets -- -D warnings

# 3. Запуск тестов
cargo test
```

### 4.2. Обработка ошибок (Запрет `.unwrap()` и `.expect()`)
- Использование `.unwrap()` или `.expect()` в основном коде приложения, демоне и модулях IPC **категорически запрещено** (допускается только в модульных тестах `#[cfg(test)]`).
- Ошибки должны заворачиваться через `anyhow::Result` или пользовательские enum-типы `thiserror` с понятными сообщениями.

### 4.3. Логирование
- Логирование осуществляется **только** через макросы крейта `tracing`: `tracing::info!`, `tracing::warn!`, `tracing::error!`, `tracing::debug!`.
- Запрещено использовать прямой вывод `println!` в коде приложения.

## 5. Версионирование

### 5.1. Схема версий (CalVer + SemVer)

Проект использует гибридную схему версионирования, совместимую со стандартом **SemVer 2.0** (требование Cargo) и основанную на календаре (CalVer):

```
<ГОД>.<ОБНОВЛЕНИЕ>.<ПАТЧ>[-beta.<НОМЕР_СБОРКИ>]
```

| Компонент | Описание | Примеры |
| :--- | :--- | :--- |
| `ГОД` | Последние две цифры года | `26` (2026) |
| `ОБНОВЛЕНИЕ` | Номер крупного обновления в году (обнуляется каждый год) | `1`, `2`, `3` |
| `ПАТЧ` | Хотфикс к конкретному обновлению | `0`, `1` |
| `-beta.N` | Пререлизная метка сборки (обнуляется с каждым `ОБНОВЛЕНИЕМ`) | `-beta.1`, `-beta.2` |

**Примеры жизненного цикла:**
```
26.1.0-beta.1  → 26.1.0-beta.2  → 26.1.0       (стабильный релиз)
26.1.0         → 26.1.1                          (хотфикс)
26.1.1         → 26.2.0-beta.1  → 26.2.0        (следующее обновление)
```

### 5.2. Файлы, содержащие версию

Версия проекта синхронизируется в **трёх** файлах:

| Файл | Поле | Пример |
| :--- | :--- | :--- |
| `Cargo.toml` | `[package] version` | `version = "26.1.0-beta.2"` |
| `meson.build` | `project(..., version:)` | `version: '26.1.0-beta.2'` |
| `data/ru.mark.vrxx.metainfo.xml.in` | `<release version=...>` | `<release version="26.1.0-beta.2" date="...">` |

При сборке через `cargo build`, версия автоматически подтягивается из `Cargo.toml` через макрос `env!("CARGO_PKG_VERSION")` в `src/config.rs` и используется в CLI (`clap`) и окне «О программе» (`Libadwaita AboutDialog`).

### 5.3. Процедура обновления версии

Для обновления версии используется утилита [`cargo-release`](https://crates.io/crates/cargo-release), которая автоматически синхронизирует все три файла, создаёт git-коммит и тег:

```bash
# Установка (один раз)
cargo install cargo-release

# Бамп версии — одна команда на всё
cargo release 26.2.0-beta.1 --execute
```

Правила подстановки версии в `meson.build` и `metainfo.xml.in` настраиваются в секции `[package.metadata.release]` файла `Cargo.toml`.

> **Важно:** Никогда не меняйте версию вручную в отдельных файлах — всегда используйте `cargo release` для гарантии синхронизации.

### 5.4. Генерация Changelog

Для автоматической генерации `CHANGELOG.md` из истории коммитов используется [`git-cliff`](https://git-cliff.org/):

```bash
# Установка (один раз)
cargo install git-cliff

# Генерация/обновление CHANGELOG.md
git-cliff --output CHANGELOG.md
```

Конфигурация `git-cliff` хранится в файле `cliff.toml` в корне репозитория. Changelog автоматически генерируется в GitHub Actions при создании релизного тега.

## 6. Процесс разработки (Git Flow и Conventional Commits)

### 6.1. Ветвление
1. Создавайте тематическую ветку от актуального `main`:
   ```bash
   git checkout main
   git pull
   git checkout -b feature/название-фичи
   ```
2. Делайте небольшие атомарные коммиты.
3. Перед отправкой убедитесь, что тесты и проверки проходят успешно.

### 6.2. Стандарт коммитов (Conventional Commits)

Все сообщения коммитов должны следовать стандарту [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <описание>
```

| Тип | Описание | Пример |
| :--- | :--- | :--- |
| `feat` | Новый функционал | `feat(ui): добавить страницу маршрутизации` |
| `fix` | Исправление ошибки | `fix(daemon): устранить утечку TUN-интерфейса при падении` |
| `refactor` | Рефакторинг без изменения поведения | `refactor(domain): вынести генератор конфигов в отдельный модуль` |
| `docs` | Документация | `docs: обновить CONTRIBUTING.md` |
| `style` | Форматирование, CSS, без изменения логики | `style(ui): привести CSS к стандартам Libadwaita HIG` |
| `test` | Добавление или исправление тестов | `test(ping): покрыть ICMP-пинг интеграционными тестами` |
| `chore` | Обслуживание, сборка, CI | `chore(release): bump version to 26.1.0` |
| `perf` | Улучшение производительности | `perf(backend): кэшировать DNS-ответы демона` |

> Описание может быть на русском или английском языке. Область (`scope`) указывается по модулю: `ui`, `daemon`, `domain`, `tui`, `ipc`, `services`, `build`.

## 7. Чеклист перед созданием Pull Request (PR)

- [ ] Ветка синхронизирована с `main` (`git rebase main`).
- [ ] Все файлы содержат неизменный лицензионный заголовок **MPL-2.0 / Copyright 2026 Mark**.
- [ ] Новые комментарии и docstrings написаны **на русском языке**.
- [ ] Код отформатирован (`cargo fmt`).
- [ ] Clippy не выдает ошибок (`cargo clippy --all-targets -- -D warnings`).
- [ ] В коде нет небезопасных вызовов `.unwrap()` или `.expect()`.
- [ ] Тесты успешно проходят (`cargo test`).
- [ ] В UI таймерах и замыканиях используются слабые ссылки `self.downgrade()`.
- [ ] Видимые пользователю строки локализованы через `gettext("...")` или `translatable="yes"`.
- [ ] Сообщения коммитов соответствуют стандарту **Conventional Commits** (секция 6.2).

## 8. Интернационализация (i18n)

Если вы добавляете новые строки в интерфейс:
1. В Rust-коде: `gettextrs::gettext("English original")`
2. В `.ui` XML-шаблонах: `<property name="title" translatable="yes">English original</property>`
3. После добавления строк обновите файлы переводов в каталоге `po/`.
