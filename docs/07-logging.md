# 07. Система логирования

## Обзор

VRXX генерирует большой объем диагностических данных от графического интерфейса, демона и внутреннего ядра (Sing-box). Чтобы не замедлять работу приложения и предотвратить износ SSD-накопителей, система логирования спроектирована асинхронной, буферизованной и разделенной на отдельные потоки.

Для логирования используется экосистема крейта `tracing`.

## Потоки логов

Все логи сохраняются в директорию `~/.config/vrxx/logs/` (с правами доступа `0o600` для безопасности).

| Файл | Содержимое | Описание |
| --- | --- | --- |
| `app.log` | GUI Logs | Журнал графического интерфейса. Создается, если программа запущена без аргумента `--daemon`. Содержит информацию о кликах, загрузке окон, ошибках парсинга. |
| `daemon.log` | Daemon Logs | Журнал системного демона. Создается, если программа запущена с `--daemon` (обычно от `root`). Содержит события старта/остановки ядра, настройки TUN и DNS. |
| `core.log` | Sing-box Logs | Прямой перехват `stdout` и `stderr` дочернего процесса Sing-box. |
| `all.log` | Combined Logs | Объединенный поток. Все события (app, daemon, core) пишутся сюда одновременно в хронологическом порядке. |

## Архитектура логирования (Tracing Stack)

В коде используются макросы `trace!`, `debug!`, `info!`, `warn!`, `error!` вместо обычного `println!`.

Архитектура:
1. **Подписчик (tracing-subscriber)** с форматом (`fmt::Layer`), который пишет в файл без ANSI-цветов (чтобы файл логов оставался читаемым в обычных текстовых редакторах).
2. **Аппендер (tracing-appender)** использует `non_blocking` обертку. Это значит, что вызов `info!()` не блокирует поток, а складывает сообщение в очередь. Фоновый поток забирает сообщения из очереди и записывает их на диск большими блоками (буферизация). Это "SSD-friendly" подход.
3. **MultiWriter (кастомная реализация)**: позволяет дублировать поток. Сообщение записывается одновременно в специфичный лог (например, `app.log`) и в общий лог (`all.log`).
4. **GLib Redirect**: В GTK-приложениях сам фреймворк GTK иногда генерирует предупреждения. Используя `glib::log_set_writer_func`, внутренние логи GLib/GTK перехватываются и направляются в нашу систему `tracing`.

## SSE Tracing Layer (Живые логи в UI)

Самая сложная часть — как передать системные логи от привилегированного демона (работающего от root) в графический интерфейс без постоянного чтения файла.

Решение: Кастомный слой трассировки `SseTracingLayer`.
Этот слой активен только в режиме `--daemon`. Он перехватывает **каждое** лог-событие в приложении, извлекает текст сообщения через `MessageVisitor` и отправляет его в EventManager.

## EventManager и кольцевой буфер

`EventManager` (`src/daemon/events.rs`) отвечает за рассылку событий.
Он использует `tokio::sync::broadcast::channel` с емкостью 1024 сообщения. Любой подключенный к демону клиент (GUI) получает эти сообщения мгновенно по SSE.

Кроме того, EventManager содержит `VecDeque` (кольцевой буфер) на те же 1024 элемента. При подключении нового клиента (открытии окна логов), он может запросить `/api/history`, чтобы мгновенно получить последние события, не обращаясь к диску.

## Окно логов (Log Window)

В пользовательском интерфейсе есть отдельное окно логов (`src/ui/components/log_window.rs`).
Оно выполняет две функции:
1. Читает последние события из файлов на диске (история).
2. Подписывается на `/api/events` (SSE-поток) через `DaemonClient`. Получаемые события немедленно вставляются в текстовое поле `gtk::TextView`.

Возможности окна:
- **Фильтрация**: Показ только Error/Warn/Info (кнопки вверху).
- **Автоскроллинг**: При поступлении новых сообщений текстовое поле прокручивается вниз.
- **Очистка**: Удаление логов из UI.
- **Поиск**: Поиск конкретных строк (в планах).

## Настройка уровня логирования

Уровень логирования задается пользователем в Настройках приложения (поле `log_level` структуры `AppSettings`).
Возможные значения (от самого тихого к самому шумному): `error`, `warn`, `info`, `debug`, `trace`.

Этот же уровень передается в конфигурацию Sing-box в блоке:
```json
"log": {
    "level": "info",
    "timestamp": true
}
```

## Диагностика

Если что-то не работает (например, VPN не подключается), следует:
1. Открыть Настройки и сменить уровень логгирования на `debug` или `trace`.
2. Попробовать переподключиться.
3. Открыть окно логов в приложении и скопировать текст, либо открыть `~/.config/vrxx/logs/all.log` в текстовом редакторе.
Ошибки настройки маршрутов обычно помечаются тегами `[network]`, а ошибки демона — `[core]`.
