# 03. Привилегированный демон и IPC (Архитектура с разделением привилегий)

## 1. Обзор и Назначение
- **Слой:** Backend (`src/daemon/`, `src/ipc.rs`)
- **Назначение:** Обеспечение работы ядра `sing-box` в режимах TUN и Proxy в фоне, а также управляемый доступ GUI и CLI без вызова паролей `sudo` пользовательским процессом.

Сетевые операции в Linux (настройка TUN-интерфейсов, модификация таблиц маршрутизации, изменение глобального DNS) требуют прав суперпользователя (`root`). Чтобы не запускать весь графический интерфейс GTK4 от имени root (что создает уязвимости), VRXX использует **двухпроцессную архитектуру с разделением привилегий**: графический клиент работает в контексте обычного пользователя, а привилегированный сервис `vrxx-daemon` управляет сетевыми ресурсами в фоне.

## 2. Архитектура фонового сервиса


### 2.1. Системный сервис (`vrxx-daemon`)
1. **Режим запуска:** Бинарный файл или подкоманда запуска `vrxx --daemon`.
2. **Systemd Unit:** Запускается как системная служба через юнит `/usr/lib/systemd/system/vrxx-daemon.service` при сборке пакета (`PKGBUILD`, `.deb`, `.rpm`).
3. **Привилегии:** Служба исполняется от имени пользователя `root`.

Пример системного юнита (`vrxx-daemon.service`):
```ini
[Unit]
Description=VRXX Privileged VPN & Proxy Daemon
After=network-online.target systemd-resolved.service
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/vrxx --daemon
Restart=always
RestartSec=3s
RuntimeDirectory=vrxx
RuntimeDirectoryMode=0755

[Install]
WantedBy=multi-user.target
```

### 2.2. IPC Взаимодействие (Unix Domain Socket)
- **Путь к сокету:** `/run/vrxx/daemon.sock`
- **Права доступа:** `0666` или принадлежность к группе `wheel`/`vrxx`, чтобы графический клиент мог подключаться без повышения привилегий.
- **Движок IPC:** Реализован с помощью `Tokio Async Unix Listener` (`tokio::net::UnixListener`).
- **Протокол:** REST-like API / JSON-RPC над Unix Domain Socket.

#### Основные эндпоинты IPC:
| Метод / Вызов | Путь / Имя | Назначение | Формат / Тело |
| --- | --- | --- | --- |
| `GET` | `/api/ping` | Проверка доступности демона | Возвращает `"pong"` |
| `GET` | `/api/status` / `GetStatus` | Запрос текущего состояния демона | Статус подключения, счетчики трафика (байты), выбранный профиль |
| `GET` | `/api/is_running` | Проверка работы процесса Sing-box | JSON boolean (`true`/`false`) |
| `POST` | `/api/proxy/start` | Запуск прокси/TUN режима | `{ core_type: string, config_json: string, tun_mode: bool }` |
| `POST` | `/api/proxy/stop` | Корректная остановка ядра | SIGTERM (при таймауте — SIGKILL) |
| `GET` | `/api/events` | Поток событий реального времени (SSE/IPC) | Трансляция логов Sing-box, изменений статуса и метрик |
| `GET` | `/api/history` | История логов | Массив последних событий (до 1024 записей) |

### 2.3. Беспарольный запуск ядра (Capabilities / Root Execution)
Для исключения всплывающих окон ввода пароля `sudo` используются два подхода:
1. **Запуск от демона `root` (Основной):**
   - Фоновый сервис `vrxx-daemon`, работая от `root`, запускает бинарник ядра `sing-box run -c stdin`.
   - Сформированный JSON-конфиг передается напрямую через `stdin` (pipe) дочернего процесса, не сохраняясь на диск.
2. **Альтернативный способ (Linux Capabilities):**
   - При сборке дистрибутивных пакетов (в `PKGBUILD` или скриптах post-install) задаются сетевые права бинарнику Sing-box:
     ```bash
     sudo setcap cap_net_admin,cap_net_bind_service=+ep /usr/bin/sing-box
     ```

### 2.4. Непрерывность работы (Background Persistence)
- **Сохранение сессии:** При закрытии графического приложения (`vrxx`) демон **НЕ останавливает** процесс `sing-box`. VPN-туннель или прокси продолжает функционировать.
- **Мгновенное восстановление состояния (State Restoration):** При повторном запуске GUI клиент отправляет IPC-запрос `GetStatus` к `/run/vrxx/daemon.sock` и мгновенно восстанавливает UI:
  - Текущий статус подключения (`Connected` / `Disconnected` / `Error`).
  - Счетчик переданных и полученных байтов.
  - Активный VPN-профиль и режим маршрутизации.

## 3. Управление ядром (ProxyManager)

Файл `src/daemon/core.rs` управляет дочерним процессом `sing-box`.

### Запуск и Остановка:
1. **Запуск:**
   - Если прокси уже запущен — текущий процесс принудительно останавливается.
   - Поиск бинарника `sing-box` (в `$PATH` или `~/.local/share/vrxx/bin/sing-box`).
   - `Command::spawn()` с перенаправленными `stdin`, `stdout` и `stderr`.
   - Конфигурация подается в `stdin`.
   - Фоновая задача мониторинга считывает `stdout`/`stderr` и пересылает события в `EventManager`.
2. **Остановка:**
   - Отправка сигнала `SIGTERM`.
   - 5-секундный таймер ожидания корректного завершения.
   - Если процесс завис — отправка `SIGKILL`.
   - Очистка сетевых интерфейсов и DNS-правил.

## 4. Сетевые компоненты (TunManager & DnsManager)

### TUN-режим (`src/daemon/network.rs`):
- При `tun_mode: true` создается интерфейс `vrxx-tun` (через `tun-rs`).
- Назначаются IP-адреса (`172.19.0.1/30` IPv4, `fdfe:dcba:9876::1/126` IPv6).
- Через `rtnetlink` интерфейс переводится в состояние `UP` и добавляются правила маршрутизации (`fwmark 0x255` для предотвращения петель).

### Менеджер DNS (`src/daemon/dns.rs`):
- Перенаправление DNS через `systemd-resolved` (`org.freedesktop.resolve1.Manager` по D-Bus с помощью крейта `zbus`).
- Методы: `set_link_dns` (привязка виртуальных DNS), `set_link_domains` (маршрутный домен `~.`), `reset_dns` (восстановление исходного DNS при остановке).

## 5. Стандарты реализации и CONTRIBUTING

1. **Обработка ошибок:**
   - Полный отказ от `.unwrap()` и `.expect()` в производственном коде.
   - Все ошибки IPC-сокета и системных сервисов оборачиваются с использованием `anyhow::Result` или `thiserror`.
2. **Логирование:**
   - Вывод событий осуществляется исключительно через макросы `tracing::info!`, `tracing::warn!`, `tracing::error!`.
   - Все логи процесса `sing-box` и самого демона транслируются подписчикам IPC/SSE в реальном времени.
3. **Неблокирующий главный поток:**
   - Опрос сокета клиентом выполняется полностью асинхронно с помощью `tokio::task`.
   - Запрещено выполнять синхронный ввода-вывод или блокировать главный поток UI (GTK main loop).
