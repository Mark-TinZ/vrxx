# ТЗ 01: Фоновый Демон, Управление Привилегиями без Sudo и IPC

## 1. Назначение и Архитектурный Слой
- **Слой:** Backend (`src/daemon/`, `src/ipc.rs`)
- **Назначение:** Обеспечение работы ядра `sing-box` в режимах TUN и Proxy в фоне, а также управляемый доступ GUI и CLI без вызова паролей `sudo` пользовательским процессом.

## 2. Требования к реализации (Архитектура с разделением привилегий)
1. **Фоновый системный сервис (`vrxx-daemon`):**
   - Бинарный файл или подкоманда запуска `vrxx --daemon`.
   - Установка через systemd unit `/usr/lib/systemd/system/vrxx-daemon.service` при сборке пакета (PKGBUILD / deb / rpm).
   - Запуск от имени `root`.
2. **IPC Взаимодействие (Unix Domain Socket):**
   - Сокет располагается по пути `/run/vrxx/daemon.sock`.
   - Права доступа на сокет: `0666` или принадлежность группе `wheel`/`vrxx`.
   - Протокол передачи сообщений: JSON-RPC или REST-like через Tokio Async Unix Listener.
3. **Беспарольный запуск ядра (Capabilities / root):**
   - Демон от `root` запускает бинарник `sing-box run -c stdin` и передает сформированный JSON через stdin.
   - Альтернативно в PKGBUILD прописывается `setcap cap_net_admin,cap_net_bind_service=+ep /usr/bin/sing-box`.
4. **Непрерывность работы:**
   - При закрытии GUI-приложения (`vrxx`) демон НЕ останавливает процесс `sing-box`.
   - При повторном открытии GUI отправляет запрос `GetStatus` по IPC и моментально восстанавливает состояние интерфейса (статус подключения, счетчик байтов, выбранный профиль).

## 3. Требования из CONTRIBUTING.md
- **Обработка ошибок:** Полный отказ от `.unwrap()` и `.expect()`. Ошибки IPC сокета wrap'ятся через `anyhow::Result` или `thiserror`.
- **Логирование:** Вывод событий исключительно через `tracing::info!`, `tracing::error!`. Все логи процесса `sing-box` транслируются по SSE/IPC клиентам.
- **Главный поток:** Опрос сокета клиентом должен происходить полностью асинхронно (`tokio::task`), не блокируя поток UI (GTK main loop).
